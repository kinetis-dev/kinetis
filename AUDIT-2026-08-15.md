# Kinetis Deep Audit — 2026-08-15

Scope: the full monorepo (19 packages), documentation site, quality
infrastructure, and the benchmark repository. Method: complete
verification baseline first (every package's tests + PHPStan + Psalm,
plus the env-gated persistence integration suite against live MySQL 8.4
and Postgres 16), then a line-by-line adversarial read of the
newest/least-reviewed code (the native driver stack, the Fiber pool,
the console/cache seams), with every suspicion settled by an empirical
probe against real databases — never by reasoning alone. Weighted
deliberately toward code that shipped this week, which prior external
audits never saw.

## Findings — fixed in this audit (persistence 1.3.2, commit 2888b6d)

### 1. Locale-dependent float binding silently corrupted results (bug, HIGH)

`MysqliAsyncClient::interpolate()` formatted float parameters with
`sprintf('%.17G', ...)`, which honors `setlocale(LC_NUMERIC, ...)`.
**Empirically confirmed**: under `de_DE.UTF-8`, binding `1.5` produced
the SQL fragment `1,5` — parsed by MySQL as two expressions —
and `SELECT ? + 0.25` with `[1.5]` returned `5.25` instead of `1.75`.
No error, silently wrong data, triggered by any code (or dependency)
calling `setlocale`. Fixed with PHP's locale-independent
float-to-string cast (verified exact round-trip under the same
locale), plus explicit rejection of non-finite floats. The Postgres
driver already used the safe cast — the fix also removes a
cross-driver inconsistency.

### 2. pgsql-async silently lost DECIMAL precision (bug, HIGH)

`PgsqlAsyncClient` converted `numeric` columns to float.
**Empirically confirmed**: a `DECIMAL(40,20)` value came back as
`1234567890.1234567` (float) from pgsql-async while all three other
drivers returned the exact string `1234567890.12345678901234567890`.
Money-typed columns lost precision, and the same application received
different types under FPM vs FrankenPHP. Fixed: `numeric` stays a
string, matching every other driver; `float4`/`float8` still convert.
Regression tests added covering all four drivers (both fixes), running
in CI's real-database integration job.

### 3. mysqli_poll() failure handling acted on unspecified state (bug, LOW)

`poll()` guarded the ready-connections loop against a `false` return
but still iterated the error/reject arrays — which `mysqli_poll()`
leaves in an unspecified state on failure, having started as the full
pending list. A rare poll failure could have failed every in-flight
query against healthy connections. Fixed: a `false` return now fails
the in-flight queries explicitly with a clear poll-failure error.

### 4. Transaction semantics diverge between driver families (doc, HIGH)

**Empirically confirmed**: a client-level `execute()` while a
transaction is open **joins** the transaction under the PDO drivers
(single connection — the insert vanished with the rollback) but runs
**outside** it under the async drivers (separate pooled connection —
the insert survived the rollback). Same code, opposite isolation
semantics under `DB_DRIVER=auto`. Inherent to the single-connection vs
pool architectures — not fixable in code without breaking legitimate
uses — so `docs/persistence.md` now carries a prominent warning: during
an open transaction, address the database only through the transaction
object.

### 5. Documentation gaps (fixed)

- `docs/appendix.md` had no entries for `FiberPool` or
  `ConcurrentBatch`, and its `#[Command]`/`BuildCommand` entries
  predated the `bootstrap: false` flag. All updated.
- `docs/performance-tuning.md` was only linked *from* nowhere — the
  persistence/runtime-adapters/concurrency pages it builds on never
  pointed back. See-also links added to all three.
- Sphinx builds clean (zero warnings) after all edits.

## Findings — recommended, not changed (each a deliberate scope call)

1. **`RoutesListCommand` runs the application bootstrap twice** — once
   via `bin/kinetis` (its definition defaults `bootstrap: true`), once
   internally for its own throwaway `AppScope`. Marking it
   `bootstrap: false` would remove the redundancy; its own internal
   `loadBootstrap` call is the one it actually needs. Small behavior
   change → left for a deliberate release rather than an audit side
   effect.
2. **No `DB_MAX_CONNECTIONS` config key.** The tuning docs teach
   sizing `maxConnections`, but the factory only accepts it via the
   `$poolOptions` code argument — an env-driven deployment can't tune
   pool width without editing bootstrap code. Adding the scoped key
   would close the loop; config-surface addition → Alon's call.
3. **`PgsqlAsyncClient` double-close edge**: `close()` with a
   transaction in flight closes the pinned connection's handle; the
   transaction's later `release()` closes it again. `pg_close()` on a
   closed handle may warn/throw on current PHP. The mysqli twin guards
   this with try/catch; the pg path should too. One-line hardening.
4. **`pg_connect()` is blocking** (pool fill only, rare) — `PGSQL_
   CONNECT_ASYNC` exists if connect latency under load ever matters.
5. **PDO clients never reconnect** — a dead connection stays dead for
   the client's lifetime. Correct for boot-and-die FPM (the intended
   runtime); worth a docblock sentence if anyone runs `DB_DRIVER=pdo`
   under a persistent worker.
6. **Benchmark repo**: `laravel-octane`'s image runs
   `composer require laravel/octane:^2.13` at build time — the octane
   version floats per build. Committing a second lock (or a pinned
   exact version) would make image builds reproducible.

## Architecture assessment

The two-pillar design (persistent workers + non-blocking core) is
carried through coherently: one suspend/resume idiom across sockets,
timers, and both async drivers; pool/waiter mechanics are correct
under adversarial reading (exclusive connection ownership between
acquire/release, per-connection pending keyed by identity,
broken-connection discard on every path including transaction
release); the dispatch-only stale-retry policy is sound (a statement
that never reached the server is safe to retry; one that might have is
never retried). `FiberPool`/`ConcurrentBatch` hold up against the
nasty cases: nested batches, sequential batches reusing a Fiber's
cached suspension, poisoned workers, the MAX_IDLE cap. The
`bootstrap: false` seam is correctly threaded through attribute →
definition → cache (format-versioned, stale caches recompile) →
`bin/kinetis` gate. Contract boundaries (`SqlLink`/`SqlResult`/dialect
markers) keep the query builder and TransactionGuard genuinely
driver-agnostic — the two type-behavior divergences that existed are
findings #1/#2 above, now closed.

## Test-architecture assessment

The split — fast unit suites, env-gated real-backend integration
tests that CI runs with real services, mutation testing with measured
per-package thresholds — is honest and effective; the one systemic
gap this audit exposed is that **type-fidelity across drivers had no
coverage** (which is exactly where both real bugs lived). The new
cross-driver DECIMAL/float tests close that class; extending the same
pattern to other type edges (BIGINT beyond 2^53, BOOLEAN round-trips,
NULL-in-every-position) would be the natural next hardening pass.
